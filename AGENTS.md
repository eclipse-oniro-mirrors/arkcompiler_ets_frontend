# AGENTS.md

## 1. Scope

This file is the repository-level guide for `ets_frontend`. It is primarily a routing index into the knowledge-base documents under `docs/`.

This repository implements the frontend compiler toolchain for ARK bytecode generation. Runtime execution semantics also depend on companion runtime repositories.

## 2. High-Risk Boundaries

- `es2panda` is the ArkTS-Dyn / JS / TS dynamic compiler route
- `ets2panda` is the C++-implemented ArkTS-Sta static compiler route
- do not assume a fix, rule, or architecture pattern from one route applies to the other
- in `ets2panda`, binder and checker must not rewrite AST structure; structural changes belong in lowering
- do not treat runtime behavior as fully defined by this repository alone
- compiler implementation must stay consistent with the language syntax spec; the spec documents generally live in the companion `runtime_core` repository
- if a change may alter generated bytecode, treat it as high-risk and notify the user before proceeding
- `ets2panda/public/`, bindings, `.abc` merge, protobuf layout, `arkguard`, and `legacy_bin` are compatibility-sensitive
- C++ toolchain compatibility changes are high-risk: header availability, API/namespace availability, and final link-symbol availability are separate checks
- do not hand-edit generated files; update templates, schema, IDL inputs, or other source-of-truth files instead

Ask before:

- changing `ets2panda/public/` interfaces or binding surfaces
- changing protobuf schema, serialization layout, or `.abc` compatibility behavior
- adding a new dependency
- deleting compatibility shims or legacy-bin behavior
- running destructive or environment-affecting commands outside the sandbox

### C++ compatibility verification (shift left)

Do not wait for downstream SDK builds or CI to discover a failure that an affected-target build can expose earlier. Verify in this order and widen only as required by risk:

1. identify the source of truth, affected targets, C++ standard, host branches, and generated files
2. compile **and link** executable/shared/static targets with the intended toolchain
3. run focused behavior tests
4. build the nearest downstream consumer, including the SDK target when applicable
5. run broader HAP/HAR, XTS, or release regression for bytecode/ABI/packaging risk

Record host OS/architecture, compiler, standard library, linker, commands, results, and untested branches; include the SDK version when an SDK build is involved. A higher-level downstream build does not replace the lower-level diagnostic gate; unavailable validation must be reported as a remaining risk.

Filesystem rule: C++ code that uses filesystem APIs must consider toolchain compatibility. Use `__has_include` to select `<filesystem>`/`std::filesystem` or the `<experimental/filesystem>`/`std::experimental::filesystem` fallback, then access the API through a common namespace alias. Do not assume that only the standard header is available, because older toolchains may otherwise fail during SDK compilation. Header detection does not guarantee link-symbol availability, so also verify the final link graph, required support libraries (for example `-lstdc++fs` on some GCC 8-era environments), both preprocessor branches where supported, and consistent production/test include assumptions.

## 5. Done Definition

A task is done only when:

- the requested behavior is implemented
- relevant validation has been run, or the limitation is explicitly stated
- the final response includes summary, files changed, validation result, and remaining risks
- compatibility or runtime/verifier impact is called out when relevant
