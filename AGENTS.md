# AGENTS.md

> Maintenance: When using an agent to modify code, any new code structure or functional feature must be reflected in this AGENTS.md in the same change.

## 1. Scope

This is the repository-level guide for `ets_frontend`, the frontend toolchain for ARK bytecode generation. Runtime semantics also depend on companion runtime repositories. Read the matching route knowledge before planning or editing.

Knowledge-base documents and the guide index are maintained under `docs/knowledge/`. Keep routing and links synchronized when adding, moving, or removing these documents.

## 4. Constraints and Boundaries

### 4.1 Risk gates and architecture invariants

Risk levels use 🔴 High, 🟡 Medium, and 🟢 Low throughout this guide. Risk sets validation depth. Approval is a separate decision governed by §4.4: a red directory does not by itself require approval for every edit.

| Area | Risk | Action before implementation | Validation |
|---|---|---|---|
| Bytecode/lowering/modules | 🔴 High | Notify for output changes | Compile, runtime, verifier |
| Public API/bindings | 🔴 High | Ask before interface changes | Generation and consumer tests |
| ABC/protobuf | 🔴 High | Ask before format/compatibility changes | Merge and compatibility regression |
| C++ toolchain/linking | 🔴 High | Proceed unless §4.4 applies | Compile/link and downstream consumer |
| ArkGuard/linter | 🟡 Medium | Ask if interface/dependency rules apply | Engine/rule and consumer checks |
| Dependencies/legacy | 🔴 High | Ask before additions or shim removal | Package and legacy consumers |
| Documentation | 🟢 Low | Proceed | Paths, flags, symbols, links |

- `es2panda` is the ArkTS-Dyn / JS / TS dynamic compiler route
- `ets2panda` is the C++-implemented ArkTS-Sta static compiler route
- compiler implementation must stay consistent with the language syntax spec; the spec documents generally live in the companion `runtime_core` repository
- if a change may alter generated bytecode, treat it as high-risk and notify the user before proceeding
- `ets2panda/public/`, bindings, `.abc` merge, protobuf layout, `arkguard`, and `legacy_bin` are compatibility-sensitive
- C++ toolchain compatibility changes are high-risk: header availability, API/namespace availability, and final link-symbol availability are separate checks

Architecture invariants:

1. Keep the dynamic and static compiler routes separate; inspect the intended route before borrowing implementation patterns.
2. In the static route, checker/binder changes preserve AST structure; structural rewrites belong in lowering with appropriate rebind/recheck.
3. Generated outputs derive from templates/schema/IDL; preserve source-of-truth and build dependencies.
4. Compiler output must agree with the applicable language specification and runtime/verifier consumers.

### 4.2 Evidence integrity — mandatory

Never fabricate source files, API symbols, CLI options, build targets, command execution, logs, test counts, passing results, or compatibility conclusions. Verify claims against the current checkout and actual tool output. Label examples and assumptions explicitly. Report checks as passed only when executed successfully; distinguish source inspection, build success, test execution, skipped checks, and unavailable validation. Never suppress a failing path, weaken tests, or update expected output solely to make a failure appear resolved. If evidence is missing, state the gap and its consequence.

When a build environment is unavailable, list the required commands, expected acceptance criteria, unexecuted checks, reasons, and available substitute evidence. Do not claim validated completion without that evidence. Failed checks remain failures until a fix and rerun demonstrate otherwise; record the fix/rerun outcome instead of relabeling failure as a skip.

### 4.3 Do not

- Do not assume a fix, rule, or architecture pattern from one compiler route applies to the other.
- In `ets2panda`, binder and checker must not rewrite AST structure; structural changes belong in lowering.
- Do not treat runtime behavior as fully defined by this repository alone.
- Do not hand-edit generated files; update templates, schema, IDL inputs, or other source-of-truth files instead.
- Do not fabricate evidence or report unexecuted checks as passed; follow the mandatory evidence rules above.
- Do not include unrelated refactoring or formatting in a scoped change.

Common pitfalls:

- ❌ Treating `es2abc` and static `es2panda` as interchangeable; use the route-specific compiler and tests.
- ❌ Patching a generated header; change its generator input and rebuild the consumer.
- ❌ Accepting changed expectations without tracing the regression; compare intended behavior first.

### 4.4 Ask before

- changing `ets2panda/public/` interfaces or binding surfaces
- changing protobuf schema, serialization layout, or `.abc` compatibility behavior
- adding a new dependency
- deleting compatibility shims or legacy-bin behavior
- running destructive or environment-affecting commands outside the sandbox

### 5.2 C++ compatibility verification (shift left)

Do not wait for downstream SDK builds or CI to discover a failure that an affected-target build can expose earlier. Verify in this order and widen only as required by risk:

1. identify the source of truth, affected targets, C++ standard, host branches, and generated files
2. compile **and link** executable/shared/static targets with the intended toolchain
3. run focused behavior tests
4. build the nearest downstream consumer, including the SDK target when applicable
5. run broader HAP/HAR, XTS, or release regression for bytecode/ABI/packaging risk

Record host OS/architecture, compiler, standard library, linker, commands, results, and untested branches; include the SDK version when an SDK build is involved. A higher-level downstream build does not replace the lower-level diagnostic gate; unavailable validation must be reported as a remaining risk.

Filesystem rule: C++ code that uses filesystem APIs must consider toolchain compatibility. Use `__has_include` to select `<filesystem>`/`std::filesystem` or the `<experimental/filesystem>`/`std::experimental::filesystem` fallback, then access the API through a common namespace alias. Do not assume that only the standard header is available, because older toolchains may otherwise fail during SDK compilation. Header detection does not guarantee link-symbol availability, so also verify the final link graph, required support libraries (for example `-lstdc++fs` on some GCC 8-era environments), both preprocessor branches where supported, and consistent production/test include assumptions.

## 6. Done Definition and Reporting

A task is done only when:

- The requested behavior or documentation correction is implemented.
- Relevant build, tests, lint, and compatibility checks ran successfully, or the missing validation and its consequences are explicit.
- The diff contains only intended changes; generated artifacts follow their source-of-truth workflow.
- Modified error paths preserve meaningful diagnostics/returns and applicable logging.
- Interface, configuration, and build changes include dependency/consumer checks.
- Public API, bytecode, runtime/verifier, packaging, and host compatibility impacts are assessed when relevant.
- New structure/features update the closest AGENTS and relevant knowledge-base pages.

Report the changed files and risk, executed commands/results, compatibility impact, unverified checks with reasons, and remaining work. Distinguish inspection, compilation/linking, test execution, and runtime compatibility evidence.
